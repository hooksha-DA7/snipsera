# Scrolling capture — 0.6.0

## Workflow

Launch Scrolling capture from home, the tray or an image's right-click menu. Select only the content that scrolls, leaving fixed headers, footers and scrollbars outside. Leave a gutter for controls and the growing preview. Start, scroll downward in overlapping steps, then choose Done. Cancel/Esc restores the previous windows without adding a history image. A successful result uses the existing preview, history, copy, save, pin, drag and editor workflow.

The interaction follows the supplied `scrollingcapture.mp4`: region selection, Start, manual scrolling, a growing preview on the left, optional Auto-scroll and Done/Cancel. Existing on-image preview/pin controls remain in place.

## Capture and alignment

Framelet captures the chosen physical rectangle approximately every 80 ms plus processing time, including intermediate positions during continuous scrolling. It looks for a unique vertical overlap with the last accepted viewport, using vertical detail so white margins do not dominate. Several candidate peaks are refined for fractional text rendering. Fractional displacement is carried between frames so rounded row counts do not accumulate a height error. Filtering is used for matching only; output strips copy original captured pixels. At least 48 rows or one eighth of the viewport must overlap, with sufficient unique detail; merely having that amount of overlap does not guarantee a match.

Only newly exposed bottom rows extend the image. A newer aligned viewport also refreshes the output rows it still covers, so later painting can replace visible placeholders. Done refreshes the last viewport after a certified settled match. Content already scrolled out before it painted cannot be recovered. Identical views and upward motion do not extend the image. A certified zero-offset match refreshes the reference after a hover/caret/widget update. Ambiguous matches leave the reference and collected pixels intact; they are not reported as unchanged. Transient mismatches are retried before surfacing a recovery warning. A stable mismatch warns after 750 ms, and a continuously changing mismatch warns after 1.5 seconds. Finishing allows up to 1.2 seconds to collect a settled final view. If that view cannot be matched, a warning explains that the image ends at the last good portion.

Each appended strip stores only its new rows; overlapping tail rows can be refreshed as described above. The live preview is bounded to 180 × 320 pixels and rebuilds at most once per 350 ms during collection; the final output preserves full capture resolution. Duplicate unchanged status notifications are suppressed. Output is bounded to 20,000 pixels per side, 40 million pixels, 1,000 accepted views and a ten-minute collection session. Limits stop collection and leave Done/Cancel available. No network, DOM access, OCR or destination-app plugin is used.

Auto-scroll is opt-in. In Chrome/Chromium windows, it uses native Windows wheel events instead of treating a queued `WM_MOUSEWHEEL` message as proof of movement. When the pointer is over Framelet's Auto-scroll control, it moves once into the selected content. It requires the target window to remain active and under the pointer, and pauses if the pointer leaves or mouse buttons/modifier keys are held. It never generates clicks or typing or steals focus from an unrelated application. Native input obeys Windows integrity restrictions; running Chrome elevated can prevent scrolling.

Other apps first use an accessibility scroll container in the external window recorded at selection. That provider has a separate 600 ms budget, leaving the two-second step budget available for wheel fallback. Accessibility runs on a dedicated background thread, reads capability/geometry only, and caches a missing pattern for the session. An in-flight provider call may finish later, with cancellation checked before issuing an action. The session verifies pixel movement and settling before the next step. If a provider reports success without movement, the next attempt uses the wheel path. Four unchanged attempts pause Auto-scroll with an explicit no-movement status, rather than assuming the document is complete. A moved/minimized target pauses collection. Manual scrolling remains independent. No new global capture hotkey is assigned; the existing four shortcuts/settings keep their current format.

## Constraints

- Vertical downward scrolling within one stable, visible area. Scrolling upward is ignored until returning past the last captured position.
- Keep overlap between views. Large jumps or dragging a scrollbar too far can lose the match. Return to a known portion, then continue slowly.
- Exclude fixed/sticky headers, footers, floating widgets and scrollbars. This version does not automatically remove them.
- Blank or repeating content may have no unique match. Animated media, cursors, sticky elements, horizontal movement, zoom changes and lazy-loading layout shifts can also interfere. No invisible or off-screen content is reconstructed.
- The selected area must be at least 80 × 80 physical pixels. Controls, border, dimming and preview stay outside it; the selection hole stays fully transparent so native scrolling can pass through. If no gutter fits, reselect a smaller area.
- During the session, other capture commands queue. Existing pins and dirty editors are restored after completion/cancellation. The previous preview is replaced only after success; its original remains in history.
- Stitched output is an SDR bitmap, subject to the same GDI/protected-content limits as ordinary capture. Auto-scroll does not prove that the entire document was captured.

A further smooth-scroll fixture reproduced fractional text matching failure. These now pass, along with exact integer-offset stitching and safety regressions. That repair first shipped as `0.6.0-preview.3`. Preview 4 adds [temporary overlay hiding](TEMPORARY-HIDE.md) and retains the same scrolling source files; native Chrome acceptance is still pending.

The no-window suite runs via `Framelet.Checks --scroll-backend-check "<fresh-output-directory>"`. It renders synthetic text off-screen, uses synthetic pixel sources and fake scroll drivers, and does not show windows, register native input, read the desktop or scroll Chrome. It covers continuous movement, changing stationary views, repeated/ambiguous content, short overlap, fractional rendering/cumulative height, Auto pacing, a no-op provider falling back, no-movement stopping, Done cancellation, existing image limits and layout geometry. Receipts are under `verification/runs/scroll-repair-01` in the checkout. Full desktop/UI tests were not rerun during the pause.

Independent review of the reported failure and revised backend led to further regressions for late painting, smooth gradients, low-contrast ambiguity, noisy integer offsets and warnings during continuous animation. Findings and dispositions are recorded in [scrolling repair notes](SCROLLING-REPAIR.md). The final no-window suite has 29 passing checks. No UI or design file was changed.
